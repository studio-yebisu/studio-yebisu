      3つの層は別のものを見ている
      
      
      
        
      検査API validateMemoryTreeConstraints
      stage の木を、基準の commit から読んだ初期方針（実行前に固定）で検査します。上限・深さ・フォルダーごとの MEMORY.md・保護ファイルを見ます。設定ファイルが変わったかどうかは見ません。
      
        
      frontmatter の検査 validateMemoryFileFrontmatter
      記憶として投影される各ファイルの先頭（MEMORY.md には無いこと、他は name と description だけ）を見ます。原典の pre-commit スクリプトには入っておらず、ここでは別に呼んでいます。
      
        
      原典の検査スクリプト（pre-commit）
      MEMORY_CONSTRAINTS_VALIDATOR_SCRIPT を run.mjs がそのまま .git/letta-memory-constraints.cjs に書き、直接1回と、実際の git commit で1回動かします。上の検査APIと同じ関数を含み、さらに .memfs.config.json の変更を人の承認なしでは止めます（L08）。
      
      
      
      
      検査がエラーを返さないことは、その記憶の内容が正しい・事実として正確・採用してよいという意味ではありません。人の承認でもありません。
      
    
      

    
      
      
      原典スキルから使った指示
      
      
      同梱した initializing-memory の SKILL.md（固定版・無改変）からは、構造の決まりと確認だけを、架空の読書会の記憶に当てはめました。
      
      
        
        
      • 使った：「Harness Constraints」（ルートの MEMORY.md、途中の各フォルダーの MEMORY.md、MEMORY.md に frontmatter を付けない、他は name と description だけ、foo.md と foo/ を並べない）。原典の検査APIと frontmatter の検査で確かめ、最後の条件だけは run.mjs が stage のパスで照合します（原典のコードではありません）。
        • 
        
      • 使った：ルートは案内にして詳細は子フォルダーの MEMORY.md の先に置く、段階的に読む構造。架空の記憶は制作側がこの形で実行前に固定しました。
        • 
        
      • 使った：「9. Verify」のうち構造の確認。止まった commit は未完了で、stage に残った変更はまだ記憶ではない、という読み方も表示に使っています。
        • 
        
      • 使っていない：/init の流れ（既存の記憶の調査、letta trajectories での履歴の検出と書き出し、Git からの利用者の推定、利用者への質問、コードの調査、Workflow とサブエージェント、別モデルでの分析、記憶の編集と統合、エージェント名での commit）。9. Verify のうち判断が要る確認（ルートの役割、重複、粒度、persona の質、意味の変化）も行っていません。
