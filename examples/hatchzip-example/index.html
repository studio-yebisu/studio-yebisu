今回やったこと（2026-10-24・実実行）
版
HatchZip v0.1.2（公式Windowsバイナリ。バイナリのSHA-256を検証済み）。実行したソース／タグのコミット 2b754c85b9322da64186e5e199ed22b1e45a5cce。
実行
新規作成した架空ファイルの使い捨てコピーに対して3回（ZIP・4,096ファイル／圧縮ZIP・16ファイル／tar・1,024ファイル）。いずれも list→test→check を先に済ませてから展開。
結果
出力は計5,136件、そのSHA-256がすべて一致。検証コピーは消費され、参照用の原本アーカイブは保持されました。
条件
既定の空き確保（2GB）のまま、十分に余裕のあるディスクで実行。ディスクを満たす試験や、クラッシュ・復旧の試験はしていません。
再現手順（コピーを作ってから実行）

再現用コードは reproduce.py です。このツールは展開とともにアーカイブを消費します。実際の制作素材・唯一の原本に対して実行しないでください。

  1. 新規フォルダーに架空のファイルを作り、通常のZIP／tarでアーカイブ（原本）。
  2. 原本のコピーを別の検証フォルダーへ置く（原本は手を付けない）。
  3. hatchzip list / test / check で中身・整合性・必要容量を確認する。
  4. コピーに対して hatchzip extract を実行する。コピーは段階的に削られ、完了時には消える。
  5. 出力を原本側のファイルとSHA-256で照合する。
python reproduce.py    # HatchZip CLI が必要（HATCHZIP_EXE でバイナリを指定可）
                       # 実行のたびに out/<日時>/ に新しい検証セットを作る

実行の全記録は out/ へ書き込まれ、公開物には含まれません。

制限と未確認
  • 「観測最大」は対象フォルダー内のファイルサイズ合計の、不等間隔サンプリングで観測した最大値です。瞬間最大や物理ディスクのピークを保証しません。
  • トレースの時間はこのPCの実行記録で、速度のベンチマークではありません。
  • 圧縮ZIPでは削れる量が小さくなることがあります。追加容量が常にゼロになるわけではありません。
  • 容量枠を約8.5MiBにした追加試験は途中停止しました。通常の予約容量2GBへ戻して再開すると24件が一致しました。容量逼迫時の完走、ディスクを満たす状況、クラッシュ・強制中断からの復旧は未確認です（追加試験の記録）。
  • 別ドライブへの展開では、元アーカイブの削除で展開先の容量は増えません。
  • 試したのは3件の小さな使い捨てデータです。大きな実データや7zのsolidブロックでの挙動はこの作例の範囲外です。
